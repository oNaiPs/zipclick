How fast ZipClick is

Two things decide how long an archive takes to extract on Windows: how fast the program decodes it, and how long Microsoft Defender spends checking each file the program writes. The second one often matters more, and it is not the same for every program.

On its own, ZipClick is the fastest of the programs here at .zip, the format most people get, and keeps up with them on .tar.gz and .tar.zst. It is slower at .7z, .tar.xz and .rar, whose decoders in ZipClick are written in Go, where 7-Zip's are optimised C and use several cores.

With Defender on, as Windows comes, an archive with thousands of small files takes several times longer with ZipClick than with 7-Zip, WinRAR or tar.exe: the Linux source, 95,000 files, takes five minutes instead of one. Defender checks every file ZipClick writes much more thoroughly than the files those programs write. Archives with a few big files, like the FFmpeg one, barely notice. More about that below.

Microsoft Defender

Defender's real-time protection checks files as programs write them. Windows' own performance recorder, run while each program extracted the Go archive, showed the difference: Defender spent 77 to 81 seconds checking the 15,000 files ZipClick wrote, 4.5 seconds on 7-Zip's, and checked only 54 of tar.exe's. Those seconds are spread over several cores, which is why they can add up to more than the time the extraction took.

Defender doesn't say why it treats programs differently. Being well known seems to count, being signed doesn't seem to be enough on its own: Bandizip is signed, and Defender slows it down about as much as ZipClick. ZipClick isn't code-signed yet, and how much a signature would change this hasn't been measured.

If you extract big source trees or SDKs often and know what that means for your security, a Defender exclusion for the ZipClick process gives you the "Defender off" times above. The files are still checked when they are opened or run. Turning real-time protection off is not something to do for this.

How it was measured

  • The computer: Windows 11 25H2 in a virtual machine with 8 cores of an Intel Core i5-12600H and 6 GB of memory.
  • The programs: ZipClick 0.4.1-11-gd4664c0, the code as it is after 0.4.1, 7-Zip 26.04, WinRAR 7.23, Bandizip 7.47, and the tar.exe, Extract All and Expand-Archive that come with Windows 11.
  • Each program extracted each archive three times and the tables show the middle time, from start until the last file is written. Every run was checked afterwards against what 7-Zip extracts from the same archive. A run that wrote less is shown as "didn't finish": Bandizip only unpacked the .tar from inside the .tar.xz and .tar.zst. Windows Extract All was stopped after 5 minutes.
  • Windows Extract All was measured through the same Shell copy the menu item uses. WinRAR ran its background extraction, as from its context menu.
  • The archives were not marked as downloaded from the internet. When one is, ZipClick and Explorer also copy that mark to every file they extract.
  • Measured on 18 and 19 October 2026, first with Defender's real-time protection off, then on. A virtual machine's disk cache and Defender move these numbers from one session to the next, sometimes by half, but the order of the programs stays about the same.
